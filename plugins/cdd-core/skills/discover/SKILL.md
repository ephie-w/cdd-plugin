# Discover CDD capabilities

Read this plugin's bundled `catalog/capabilities.yaml` before matching any CDD capability. The catalog is a demo snapshot, not a production approval source. If the catalog is unavailable, report that the plugin failed to load and stop; do not substitute a Confluence or web search.

1. Identify the user's outcome and constraints. Compare them with each entry's `use_when` and `do_not_use_when`, not just its name.
2. Follow matching pattern-to-component and pattern-to-pattern references. A pattern may carry its own guide `plugin` and `reference_implementations`; handle them as in steps 4–6, and do not present a reference implementation as a reusable component. Keep optional components distinct from requirements. Report `known_gaps` without inventing a missing component. A `category` routes discovery; it is not evidence that a particular subfeature exists.
3. Report each entry's exact `status`; draft patterns and candidate components are not approved.
4. For a matched component with `authoritative_sources`, read the sources relevant to the user's question before making claims beyond the catalogue. For metadata enrichment, search the listed service GitHub repository for the current contract, configuration, or extractor documentation relevant to the question (including named-entity support); use `docs/PROJECT_ONBOARDING.md` there for onboarding. The listed Confluence page is a high-level capability overview only: do not use it as evidence for onboarding steps, ownership, or access requests. Use the session's available repository access or connected tools; the bundled Atlassian MCP declaration still requires an authenticated connection. Cite the exact GitHub file and revision or Confluence page used, not merely the repository homepage, and distinguish source findings from the catalogue snapshot. If a required source cannot be read, report its URL and the unanswered question as **unverified**; do not infer support or process details from the source title, category, or component skill text. If sources conflict, report the conflict and keep the affected claim unverified.
5. Report `plugin.name`, `plugin.marketplace_path`, and `plugin.skill`. Check whether that plugin is installed in the current session before invoking its skill. A catalogue record, a required or optional marketplace entry, or skill text found in a repository does not mean the plugin is active in this session. Reading an authoritative source is discovery evidence, not execution of the component skill. In CLI/Desktop, `plugin.local_agent` is an optional specialist for a larger read-only assessment; in Cloud, use an installed skill directly because plugin custom subagents are not loaded there. Never make the local agent a prerequisite.
6. If the plugin is absent, state **plugin not installed; component skill not run**. Do not present a manual reading of its repository copy as the skill's assessment or conclude the component is adoptable. Give an installation handoff containing the plugin name, skill command (`/<plugin.name>:<plugin.skill>`), and the exact `git-subdir` source: `plugin_source.source`, `plugin_source.url`, `plugin_source.ref`, and `plugin.marketplace_path` as `path`. For Cloud, direct the user or admin to install that source through Devin's plugin management/Marketplace. If a plugin-management tool is available and the user has explicitly asked for installation, it may be used; otherwise ask before changing plugin state. For a local CLI checkout, `devin plugins install ./<plugin.marketplace_path>` is an option from the repository root. Check activation after installation; if the current session still lacks the skill, tell the user to start a new session and rerun the assessment. Never promise same-session activation.
7. If no entry fits, say the catalogue has no match. Do not force a CDD recommendation.

Return matched IDs, reasons for fit or exclusion, status, gaps, authoritative sources read or inaccessible, remaining unverified claims, whether the component skill actually ran, the next plugin/skill or installation handoff, and anything still needing confirmation. Discovery alone must not edit application code or install plugins without an explicit user request.
